# Create Delta Table Using Spark SQL

This guide follows the steps for creating a database-like schema, creating a Delta table, loading JSON data into it, and checking the result. It also explains how Unity Catalog organizes tables and manages storage.

## Steps

We will work through these tasks:

1. Review supported providers.
2. Create a database (schema) and review its details.
3. Create a managed table and review its metadata.
4. Copy data from JSON files into a managed table.
5. Validate the data in the managed table.
6. Create an external table and review its metadata.
7. Insert data from JSON files into an external table.
8. Validate the data in the external table.
9. Compare managed and external tables.

> The code and object names below are kept as provided. The explanations describe what each part is intended to do.

## Database and schema terminology

In PostgreSQL, a database and a schema are different levels:

```text
PostgreSQL server
└── Database
    └── Schema
        └── Tables
```

A PostgreSQL connection is to one database. That database can contain multiple schemas, and each schema can contain tables.

In Databricks Unity Catalog, `DATABASE` is a synonym for `SCHEMA`. The hierarchy is:

```text
Unity Catalog
└── Catalog — workspace
    └── Schema (also called database) — itversity_retail_db
        └── Tables
```

The three-part name of a Unity Catalog table is `catalog.schema.table`. For example, `workspace.itversity_retail_db.orders` identifies the `orders` table in the `itversity_retail_db` schema under the `workspace` catalog.

## Setup Comparison

### Old version: DBFS

```sql
SET spark.sql.warehouse.dir -- Default is dbfs:/user/hive/warehouse
```

This shows the older Hive-style warehouse setting from the lesson. It refers to a default storage location used by the older Hive metastore setup.

### New version: Unity Catalog

You **don’t set `spark.sql.warehouse.dir` to a volume path**. That setting is for the older Hive-style default location. Unity Catalog manages the storage location for its managed tables, and you access volume files by their `/Volumes/...` path.

A **volume** is for working with files, such as the JSON files in this exercise. A **table** is a structured dataset registered in the catalog. The table and the source files therefore have separate names and roles.

## Create the schema/database

### Check the catalogs

```sql
SHOW CATALOGS;
```

This lists the catalogs available to you. In this exercise, the catalog is `workspace`.

### Create the schema

```sql
CREATE SCHEMA IF NOT EXISTS workspace.itversity_retail_db;
```

This creates the `itversity_retail_db` schema inside `workspace` if it does not already exist. In Unity Catalog, this schema is also commonly called a database.

### Set the current catalog and schema

```sql
USE CATALOG workspace;
USE SCHEMA itversity_retail_db;
```

These statements set the default catalog and schema for later commands in the current session. After this, you can refer to a table by its short name, such as `orders`.

### Describe the database/schema

```sql
DESCRIBE DATABASE itversity_retail_db
```

This displays information about the schema, such as its catalog, owner, and location when one is specified.

## Create the Delta table

```sql
--- make sure to select correct database
use itversity_retail_db;
SELECT current_database()

--- create the delta table
CREATE OR REPLACE TABLE orders(
    order_id BIGINT,
    order_date STRING,
    order_customer_id BIGINT,
    order_status STRING
) USING DELTA

--- check it

DESCRIBE orders
```

The table definition lists the columns and their data types. `USING DELTA` specifies the Delta format. `CREATE OR REPLACE TABLE` creates the table, or replaces the existing table with the same name. `DESCRIBE orders` displays the table’s columns and types.

`SELECT current_database()` displays the current schema/database context, helping you confirm where the short table name `orders` refers.

## Load data into the table

### Review the table details

```sql
--- Get Full Details Of The Table
DESCRIBE FORMATTED orders
```

This displays additional metadata about the table, including information about its storage and provider.

### Upload the Retail DB JSON files from your computer to the workspace volume

Run this command in a terminal from your project directory:

```bash
databricks fs cp data/retail_db_json dbfs:/Volumes/workspace/default/retail_db/retail_db_json --recursive --profile "firdaucazizah@gmail.com"
```

This copies the local `data/retail_db_json` folder and its contents to the Unity Catalog volume path. The `--recursive` option includes files inside subfolders, and `--profile` selects the saved Databricks CLI profile.

### Validate that the files are present

Run this in a Databricks notebook cell:

```sql
%fs ls /Volumes/workspace/default/retail_db/retail_db_json/orders/
```

`%fs ls` lists the files at the specified volume path. This is a notebook command, not a terminal command.

### Check the first few lines of a file

```sql
%fs head dbfs:/Volumes/workspace/default/retail_db/retail_db_json/orders/part-r-00000-990f5773-9005-49ba-b670-631286032674
```

`%fs head` displays the beginning of the specified file so you can inspect its contents.

### Read the file with a query

```sql
SELECT * FROM JSON.`dbfs:/Volumes/workspace/default/retail_db/retail_db_json/orders/part-r-00000-990f5773-9005-49ba-b670-631286032674`
```

This reads the JSON file as a queryable data source. The backticks enclose the file path following the `JSON.` format name.

### Copy the JSON data into the table

```sql
COPY INTO orders
FROM 'dbfs:/Volumes/workspace/default/retail_db/retail_db_json/orders/'
FILEFORMAT = JSON
```

`COPY INTO` loads data from the source folder into the existing `orders` table. `FILEFORMAT = JSON` tells Databricks how to read the source files.

## Validate data in the Spark metastore managed table

### Check the table details

To check whether it is a managed Delta table and see its storage details, run:

```sql
DESCRIBE DETAIL workspace.itversity_retail_db.orders;
```

Look for `format` (`delta`) and `tableType` (`MANAGED`). Unity Catalog tables use the `catalog.schema.table` name, and managed tables have their storage location determined by Unity Catalog.

### Check the table listing, columns, and rows

```sql
-- Confirm the table is listed in the schema
SHOW TABLES IN workspace.itversity_retail_db;

-- Check its columns and data types
DESCRIBE TABLE workspace.itversity_retail_db.orders;

-- Check that rows loaded
SELECT COUNT(*) AS row_count
FROM workspace.itversity_retail_db.orders;

-- Preview some rows
SELECT *
FROM workspace.itversity_retail_db.orders
LIMIT 10;
```

These checks answer different questions:

- `SHOW TABLES` checks that the table is registered in the schema.
- `DESCRIBE TABLE` shows the table’s column names and data types.
- `COUNT(*)` reports how many rows are in the table.
- `LIMIT 10` displays a small sample of the data.

### Using the short table name

Because the earlier statements set the current catalog and schema, you can omit `workspace.itversity_retail_db` and query `orders` by itself, as in your note. The fully qualified name makes the table’s catalog and schema explicit, which is useful when you want to avoid ambiguity.

## Managed and external tables

A **managed table** is a table whose data storage and lifecycle are managed by Unity Catalog. You create and query it by its table name, such as `workspace.itversity_retail_db.orders`.

An **external table** is registered in Unity Catalog but points to a storage location that you specify. Unity Catalog manages its metadata and access, while the data files remain at that external location.
